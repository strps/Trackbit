# Exercise Programs, Favorite Lists & Picker Sources

This plan replaces the hardcoded "Recommended" list in the activity tracker's exercise picker with a pluggable **exercise source** system. The same abstraction serves every user level:

- **Casual** — named favorite lists ("Home gym", "Leg day"): plain ordered lists, no prescriptions.
- **Intermediate** — routines with optional prescriptions (target sets/reps/weight/rest) that pre-fill logs.
- **Advanced** — full programs: routines scheduled onto weekdays or calendar dates, with progression.
- **Coached (future)** — programs authored by an external user (human trainer) or generated by a smart/AI agent.

Two design decisions carry the whole thing:

1. **Favorite lists and program routines are the same entity** — an ordered exercise list where prescriptions are nullable per item. Programs are a scheduling layer on top of lists.
2. **The picker branches on capabilities, never on source type.** A new source kind is a backend-only change: it appears in the source listing endpoint and resolves to the same `ResolvedQueue` shape.

Current state (what changes):

- [AddExercisePicker.tsx](../../apps/frontend/src/features/activity-tracker/components/AddExercisePicker.tsx) shows a `Label` with `t('activity_recommended')` and cycles `selected` through **all** exercises (`(idx + 1) % exercises.length`). Both the label and the queue logic get replaced.
- [exercises.ts schema](../../apps/backend/src/db/schema/app/exercises.ts) has no list/program tables yet.

## Core Concepts

| Concept | What it is |
|---|---|
| **Exercise list** | Ordered, named list of exercises owned by a user. Doubles as a favorite list and as a program routine. |
| **List item** | One exercise in a list, with a position and an **optional** prescription (sets/reps/weight/duration/distance/rest/notes). Casual users never see prescriptions. |
| **Program** | A named container that schedules lists (routines) onto weekdays or explicit dates. |
| **Exercise source** | Anything that can answer "what's the ordered queue of exercises right now?": a list, today's program routine, and later server-computed feeds. |
| **Browse mode** | The absence of a source. The picker falls back to searching the full exercise catalog. **Not** a source — see below. |

### "All exercises" is not a source

The full catalog has no order, no owner, and nothing to advance through, so modelling it as a source would mean every consumer carries a special case for the one member that behaves differently. Instead, the active source is `ExerciseSourceRef | null`, and `null` is browse mode:

| | Browse mode (`null`) | Source active |
|---|---|---|
| Picker popover | search the full catalog, add anything | queue in source order; search still falls back to the catalog, visually separated |
| Trigger button | the last exercise picked (or last logged this session) | `entries[cursor]` |
| Play button | logs whatever the trigger names — repeats the current pick | logs `entries[cursor]`; the cursor advances, so presses walk the queue |
| Header label | `t('activity_all_exercises')` | source name |

Play is **not** hidden in browse mode. The two controls divide as: Play is the quick "add another, one after the next" button, and the popover is for adding something out of order or outside the source via search. Hiding Play would remove the primary control for exactly the users who have not built a list yet. What browse mode lacks is a *queue*, not a selection — so the trigger holds the selection itself and Play stays meaningful in both modes.

This is also what removes the current crash: there is no `exercises[selected]` to dereference when the catalog is empty ([AddExercisePicker.tsx:50](../../apps/frontend/src/features/activity-tracker/components/AddExercisePicker.tsx#L50), [:78](../../apps/frontend/src/features/activity-tracker/components/AddExercisePicker.tsx#L78), [:108](../../apps/frontend/src/features/activity-tracker/components/AddExercisePicker.tsx#L108)).

## The `ExerciseSource` abstraction

Shared shapes live in `packages/types`.

### Identity

A discriminated union, so "which id applies" is enforced by the compiler rather than by a comment:

```ts
type ExerciseSourceRef =
    | { kind: 'list'; listId: number }
    | { kind: 'program'; programId: number }
    | { kind: 'computed'; strategy: string };   // 'least-recent-muscle-group' | 'agent-v1' | …
```

Note what is *absent*: there is no `'trainer'` kind. Trainer authorship is an attribute of a row (`authorId`), not a resolution mechanism — a trainer-built routine is still a list. Likewise `'smart'` and `'agent'` collapse into `'computed'`, because both mean "the server computes the queue"; only the strategy string differs. Phase 5 therefore adds **zero** members to this union.

Each ref has a canonical string form used as a React key, a persistence value, and a URL segment:

```
list:12      program:3      computed:least-recent-muscle-group
```

`parseSourceKey` / `serializeSourceKey` live in `packages/types` and are the only places that know the format. Validate with a zod schema on both ends (`^(list|program):\d+$|^computed:[a-z0-9-]+$`).

### Descriptor — what the dropdown lists

```ts
interface SourceCapabilities {
    canAppend: boolean;    // show the "add this exercise to the source" affordance
    canReorder: boolean;
    prescribes: boolean;   // entries may carry prescriptions worth pre-filling
    isDynamic: boolean;    // content changes without user edits (program/computed) → short cache TTL
}

interface ExerciseSourceDescriptor {
    ref: ExerciseSourceRef;
    key: string;               // canonical serialization
    name: string | null;       // user content, never translated; null ⇒ render nameKey
    nameKey?: string;          // i18n key for system-named sources: 'source_todays_routine', …
    itemCount: number | null;  // null when unknowable before resolution
    capabilities: SourceCapabilities;
    frozen: boolean;           // over-limit resource → read-only, per the freeze pattern
}
```

`capabilities` is what keeps the picker type-agnostic. Without it the picker still has to ask "is this a list?" to decide whether to offer *add to list*, which is exactly the coupling the abstraction exists to prevent. Every flag is **derived at read time**, never stored:

| Flag | Derivation |
|---|---|
| `canAppend` | `kind === 'list' && !frozen` |
| `canReorder` | `kind === 'list' && !frozen` |
| `prescribes` | any item in the list (or today's routine) has a non-null target column |
| `isDynamic` | `kind !== 'list'` |

### Resolution

```ts
interface Prescription {          // mirrors exercise_list_items 1:1
    targetSets: number | null;
    targetReps: number | null;
    targetWeight: number | null;
    targetDuration: number | null;   // seconds
    targetDistance: number | null;
    restSeconds: number | null;
    notes: string | null;
}

interface QueueEntry {
    exerciseId: number;              // client joins its own exercise cache
    position: number;
    listItemId: number | null;       // provenance; null for computed sources
    prescription: Prescription | null;
}

interface ResolvedQueue {
    descriptor: ExerciseSourceDescriptor;
    entries: QueueEntry[];
    resolvedFrom?: {                 // program → which routine today resolved to
        listId: number;
        listName: string;
        programEntryId: number;
    };
    emptyReason?: 'rest_day' | 'no_routine_scheduled' | 'list_empty' | 'no_data';
    generatedAt: string;             // ISO
    expiresAt?: string;              // computed sources; cheap now, painful to retrofit
}
```

Three deliberate omissions from the earlier draft:

- **No `label: string`.** The backend would have to resolve the user's locale to render it, which contradicts the i18n conventions. `name` is user content passed through verbatim; `nameKey` covers system-named sources and is translated client-side.
- **No embedded `Exercise`.** The client already caches the catalog via `useExercises`, and `nameI18n` resolution is client-side anyway. Sending ids avoids duplicated payloads and stale-name skew, and gives the native app the identical contract.
- **No `nextIndex`.** See below.

`prescription` fields are `T | null`, never optional — one representation for "not prescribed" instead of two (`undefined` vs `null`) drifting through JSON round-trips.

**Prescription units** are the exercise's `defaultWeightUnit` / `defaultDistanceUnit`. The prescription itself stores no unit; the log the user creates carries its own (`exercise_log.weightUnit` / `.distanceUnit`), pre-filled from the same defaults.

### The cursor is client-side

`nextIndex` does not belong on the server: it welds a cacheable resource (what's *in* the source) to mutable session state (what's been *logged*). Putting it in the payload means every `addExerciseLog` invalidates the queue and refetches, and it creates a second source of truth for "what's logged today" alongside the session the client already holds.

`useExerciseQueue` derives it instead:

```ts
// Returns -1 for an empty queue.
function nextQueueIndex(entries: QueueEntry[], sessionLogs: ExerciseLog[]): number {
    if (entries.length === 0) return -1;

    // An entry is "done" when a log in this session came from that exact list item.
    // Falls back to exerciseId for computed sources, which have no listItemId.
    const doneItemIds = new Set(sessionLogs.map(l => l.listItemId).filter(Boolean));
    const doneExerciseIds = new Set(sessionLogs.map(l => l.exerciseId));

    const isDone = (e: QueueEntry) =>
        e.listItemId !== null ? doneItemIds.has(e.listItemId) : doneExerciseIds.has(e.exerciseId);

    const i = entries.findIndex(e => !isDone(e));
    if (i !== -1) return i;

    // Exhausted → plain cycling from the most recently logged entry.
    const lastIdx = /* index of the entry matching the newest session log */ 0;
    return (lastIdx + 1) % entries.length;
}
```

Matching on `listItemId` rather than `exerciseId` is what makes the cursor correct when a routine legitimately repeats an exercise (top set + backoff set). It is only possible because logs carry provenance — see Phase 1.

### Dangling refs

The persisted selection *will* dangle: lists get deleted, programs get deactivated, a trainer relationship ends. Every read path resolves a stored key through one guard that returns `null` (→ browse mode) rather than throwing, and clears the stored preference on the next write. Resolution endpoints return `404` for an unknown/unowned ref; the hook treats `404` as "fall back to browse mode", not as an error toast.

### Endpoints

Two endpoints are the entire abstraction boundary. Adding a source kind touches neither the picker nor these signatures.

| Endpoint | Returns |
|---|---|
| `GET /api/exercise-sources` | `ExerciseSourceDescriptor[]` — every list, the active program (if it has a routine today), and any enabled computed strategies |
| `GET /api/exercise-sources/:key` | `ResolvedQueue` |

`list:` refs resolve client-side from cached list data when available; the endpoint remains the canonical implementation for the native app and cold loads.

The barrel is what `db.ts` passes to `drizzle({ schema })`, so an unregistered file means no relational queries and no `drizzle-kit` diff.

Lists get their own file rather than joining [exercises.ts](../../apps/backend/src/db/schema/app/exercises.ts) (already 177 lines / 5 tables): this is a distinct domain that grows in Phase 4 (`programs`, `program_entries`) and Phase 5 (sharing permissions). The circular import that would have argued for merging them is a non-issue — see the note below.

- [x] **`exercise_lists`**
  - `id` serial PK
  - `userId` → `user.id` (owner, cascade delete)
  - `authorId` → `user.id`, nullable — set when someone else (trainer) created it; equals owner for self-made lists. Nullable now so Phase 5 needs no migration.
  - `name` text not null, `description` text
  - `position` integer not null (ordering lists in UI, and the freeze order)
  - `createdAt`, `updatedAt`
  - Unique index on `(userId, name)`.
  - **No `kind` column.** A "routine" is a list referenced by a `program_entry` or carrying prescriptions — both derivable. A stored hint is a second state that can disagree with the data, and it earns nothing: the shape is identical either way.
- [x] **`exercise_list_items`**
  - `id` serial PK — **not** `(listId, exerciseId)`. A composite key silently forbids the same exercise twice in one list, which routines need (heavy set + backoff, circuits flattened into a single order).
  - `listId` → `exercise_lists.id` (cascade), `exerciseId` → `exercises.id` (cascade)
  - `position` integer not null
  - Prescription columns, **all nullable**: `targetSets` int, `targetReps` int, `targetWeight` real, `targetDuration` int (seconds), `targetDistance` real, `restSeconds` int, `notes` text
  - `unique(listId, position)` declared **`DEFERRABLE INITIALLY DEFERRED`** in the migration, exactly like `habits_user_anti_order_uq` ([habits.ts:40-42](../../apps/backend/src/db/schema/app/habits.ts#L40-L42)). Replace-all reordering still passes through conflicting intermediate states inside the transaction; a non-deferrable constraint makes any reorder fail.

Change to `exercise_log` ([exercises.ts:119](../../apps/backend/src/db/schema/app/exercises.ts#L119)):

- [x] `listItemId` integer nullable → `exercise_list_items.id` **on delete set null**. This is the provenance that (a) makes the queue cursor exact with repeated exercises and (b) makes Phase 4 adherence reporting ("did they follow the program?") possible at all. Free now, a backfill later.
- *Import cycle:* `exercise-lists.ts` imports `exercises.ts` (for `exerciseId`) and `exercises.ts` imports back (for `listItemId`). This is fine — verified against `drizzle-orm@0.45.1` with `tsc --strict`. `.references(() => …)` takes a lazy callback that runs after both modules finish evaluating, so no TDZ, and neither table appears in its own type initializer, so no `: any` annotation is needed (unlike `muscleGroups`' self-reference at [exercises.ts:41](../../apps/backend/src/db/schema/app/exercises.ts#L41)). Both files are re-exported from `schema/index.ts`, so load order is irrelevant. Declare the FK normally; no migration-level workaround.

**Prescriptions never materialize.** Logging a prescribed exercise creates the `exercise_log` row and nothing else — no placeholder `exercise_performances`. The user logs what they actually did; targets are display hints and pre-fill values only. Materializing them would put planned-but-not-performed sets into performance history, corrupting PRs, volume totals and every downstream stat. Adherence is answered by joining logs to `listItemId`, not by pre-writing rows.

**Implementation notes** (where the shipped code deviates from the plan above, and why):

- **`PUT /:id/items` diffs on item id instead of deleting every row.** Replace-all stays the client-facing contract, but `exercise_log.list_item_id` is `ON DELETE SET NULL`: a blind delete-and-reinsert would erase the provenance of every past log on each reorder, defeating both the cursor and Phase 4 adherence. Items carry an optional `id` — present means keep the row, absent means new, missing means delete.
- **`listItemId` is write-once.** Creation validates the item belongs to one of the caller's own lists; the generated PATCH schema omits it, since otherwise a client could re-point an existing log at any item id, including another user's.
- **List reads use explicit selects, not `db.query.*.with`.** Nested relational results infer as `{ [k: string]: any }` against this schema, which erases the item type at every call site. `loadOwnedListsWithItems` / `loadOwnedListWithItems` in the sources lib are the shared loaders.
- **No `owner` / `author` relations on `exercise_lists`.** Both FKs target `user`, so pairing them needs matching `relationName`s on the user side; nothing traverses that direction until Phase 5, which can add both halves together.

**Implementation notes:**

- **The preference rides on the session, not on a second fetch.** `preferredExerciseSource` is declared in better-auth `additionalFields` (backend `auth.ts` + frontend `inferAdditionalFields`) with `input: false`, so it comes back on `useSession()` and only ever changes through `PATCH /api/me/preferences`. This is deliberately *not* the card-style pattern, which keeps its value in `localStorage` and can therefore disagree with the column it writes to.
- **One store, one guard.** [use-preferred-exercise-source.ts](../../apps/frontend/src/hooks/use-preferred-exercise-source.ts) is a small zustand store (shared, because two session panels must not disagree about a user preference) hydrated once from the session. The stored key is resolved against the descriptor list on every read: no descriptor ⇒ browse mode. Clearing a dangling key waits for descriptors to have actually loaded — a slow or failed `/exercise-sources` fetch must not wipe a valid preference.
- **`useExerciseQueue` takes session logs, not a session id.** Pure inputs keep it out of the activity-tracker feature's dependency graph and make it reusable by the native picker; the caller resolves `sessionId → logs` from the tracker cache it already holds. A `404` resolves to `null` data rather than rejecting, so a deleted list produces browse mode instead of an error toast.
- **Prescription pre-fill lands in `newPerformance`, not in `addExerciseLog`.** "Pre-fill the editor" cannot mean writing rows at log time — that is exactly the planned-sets-in-history failure the plan forbids. Instead `buildNewSetValues` resolves `log.listItemId → list item → prescription` and lets targets outrank `lastPerformance` for the set the user is actually recording. The same builder feeds the request and the optimistic update, so they can no longer show different numbers. `targetDuration` is seconds and `exercise_performances.duration` is milliseconds — the builder converts.
- **List writes invalidate resolved queues.** `useExerciseLists.invalidateAll` now also drops the `['exercise-source']` prefix, so editing a list's items updates an open picker instead of serving a stale queue for the 30s TTL.
- **The trigger holds a selection; Play adds it.** One model for both modes, which is what keeps the quick-add and the search popover distinct instead of overlapping. With a source, the selection is `entries[cursor]` and is derived from the logs, so each press walks the queue and an out-of-order pick from the popover just moves the cursor past that entry. In browse mode the selection is local state seeded from the last log in the session, so a resumed session finds Play already armed. Play is absent (never disabled) only when nothing is selected at all.
- **Done entries are marked, not hidden.** The popover dims logged entries and shows a check; the cursor entry keeps the ring the old "recommended" row had. Hiding them would make the queue's own order unreadable mid-session.

### Phase 5: External authors & future sources

Groundwork exists (`authorId` everywhere, `computed` kind reserved); this phase makes it real.

- [ ] **Trainer sharing:** invitation/link between two users; trainer gets scoped write access to the trainee's lists/programs (`authorId` = trainer). Needs a permissions table (new `apps/backend/src/db/schema/app/coaching.ts`, barrel-registered) + API guards, and a read-only "who wrote this" view for the trainee. No new source kind — trainer-authored lists appear in the listing like any other. Also the point at which `exercise_lists` gains its `owner` / `author` relations.
- [ ] **Computed sources:** each is a strategy string behind `GET /api/exercise-sources/computed:<strategy>`.
  - [ ] `least-recent-muscle-group` — server-computed from history; `exercise_muscle_groups` data is already in place. Cheapest win, zero frontend changes.
  - [ ] `agent-v1` — same contract, generated by an LLM from history + goals. Product decisions (cost, cadence, prompt inputs) deliberately deferred; only the endpoint shape is reserved. `expiresAt` on `ResolvedQueue` is what keeps regeneration cost bounded.
- Marketplace/template sharing of programs between users: future work, out of scope.

## Cross-cutting notes

- **Limits/freeze:** every new creatable resource (lists, programs) registers in `user_limits` and honors the frozen-resource enforcement from the role-limits work (2026-05).
- **i18n:** all new UI strings go through i18next with symmetric bundles across locales. System exercise names already have `nameI18n`; list/program names are user content and are never translated — which is why the backend returns `name` verbatim and `nameKey` only for system-named sources.
- **Native app:** the Expo app will need the picker eventually. Keeping resolution behind the two `exercise-sources` endpoints and the shared `ResolvedQueue` type in `packages/types` makes parity cheap — the native picker consumes the same descriptors and derives the same cursor.

## Resolved decisions

| Question | Decision |
|---|---|
| Do prescriptions materialize as `exercise_performances` rows? | **No.** Pre-fill only; the user logs actual data. Planned sets must never enter performance history. |
| Provenance (`listItemId`) on `exercise_log`? | **Yes.** Enables an exact queue cursor with repeated exercises, and Phase 4 adherence reporting. |
| Is "All exercises" a source? | **No.** It is browse mode — `activeSource === null`. Removes the one member that behaves unlike the others. |

## Open questions

- Should deleting an exercise that belongs to lists cascade out of the lists or block deletion with a warning? *(Phase 1 shipped the cascade as designed — revisit in Phase 2 when the list UI makes the consequence visible; changing it later is a migration, not a rewrite.)*
- When a trainer authors a program, can the trainee edit it, or is it read-only until the trainer relationship ends?
- Does "one active program" hold, or can advanced users run overlapping programs (e.g. lifting + running)?
