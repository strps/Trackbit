# Exercise Programs, Favorite Lists & Picker Sources

This plan replaces the hardcoded "Recommended" list in the activity tracker's exercise picker with a pluggable **exercise source** system. The same abstraction serves every user level:

- **Casual** — named favorite lists ("Home gym", "Leg day"): plain ordered lists, no prescriptions.
- **Intermediate** — routines with optional prescriptions (target sets/reps/weight/rest) that pre-fill logs.
- **Advanced** — full programs: routines scheduled onto weekdays or calendar dates, with progression.
- **Coached (future)** — programs authored by an external user (human trainer) or generated by a smart/AI agent.

The key design decision: **favorite lists and program routines are the same entity** (an ordered exercise list; prescriptions are nullable per item). Programs are a scheduling layer on top of lists. The picker never knows about any of this — it only consumes an `ExerciseSource`.

Current state (what changes):

- [AddExercisePicker.tsx](../../apps/frontend/src/features/activity-tracker/components/AddExercisePicker.tsx) shows a `Label` with `t('activity_recommended')` and cycles `selected` through **all** exercises (`(idx + 1) % exercises.length`). Both the label and the queue logic get replaced by the active source.
- [exercises.ts schema](../../apps/backend/src/db/schema/app/exercises.ts) has no list/program tables yet.

## Core Concepts

| Concept | What it is |
|---|---|
| **Exercise list** | Ordered, named list of exercises owned by a user. Doubles as a favorite list and as a program routine. |
| **List item** | One exercise in a list, with a position and an **optional** prescription (sets/reps/weight/rest/notes). Casual users never see prescriptions. |
| **Program** | A named container that schedules lists (routines) onto weekdays or explicit dates. |
| **Exercise source** | Anything that can answer "what's the ordered queue of exercises right now?": all exercises, a list, today's program routine, and later smart/AI/trainer feeds. |

## The `ExerciseSource` abstraction

Designed now so smart/AI/trainer sources plug in later without touching the picker again.

```ts
// packages/types (shared shape)
type ExerciseSourceType = 'all' | 'list' | 'program' | 'smart' | 'agent' | 'trainer';

interface ExerciseSourceRef {
    type: ExerciseSourceType;
    id?: number;          // listId or programId; absent for 'all'
}

interface QueueEntry {
    exercise: Exercise;
    prescription?: {      // null for plain favorite lists
        sets?: number; reps?: number; weight?: number;
        restSeconds?: number; notes?: string;
    };
}

interface ResolvedQueue {
    source: ExerciseSourceRef;
    label: string;        // what the picker shows instead of "Recommended"
    entries: QueueEntry[];
    nextIndex: number;    // server/client-computed "next up" (skips already-logged today)
}
```

- **Frontend:** a `useExerciseQueue(sourceRef, sessionId)` hook resolves any source to a `ResolvedQueue`. `'all'` and `'list'` resolve client-side from cached data; `'program'` resolves via API (needs "today's routine" logic); `'smart' | 'agent' | 'trainer'` are stubs that later hit their own endpoints.
- **`nextIndex`** replaces today's naive modulo cycling: it's the first entry not yet logged in the current session, wrapping to plain cycling once the queue is exhausted.
- The user's last-selected source is persisted (user settings / preferences, same channel as other tracker preferences like the compact log-card style) so the picker restores it on load.

## Technical Implementation Plan

### Phase 1: Data layer — lists

New tables in `apps/backend/src/db/schema/app/` (new file `exercise-lists.ts`):

- **`exercise_lists`**
  - `id` serial PK
  - `userId` → `user.id` (owner, cascade delete)
  - `authorId` → `user.id`, nullable — set when someone else (trainer) created it; equals owner for self-made lists. Nullable-now so Phase 5 needs no migration.
  - `name` text, `description` text
  - `kind` text default `'favorite'` — `'favorite' | 'routine'`. Purely a UI hint (where it shows up); the data shape is identical.
  - `position` integer (ordering lists in UI)
  - `createdAt`, `updatedAt`
  - Unique index on `(userId, name)`.
- **`exercise_list_items`**
  - `listId` → `exercise_lists.id` (cascade), `exerciseId` → `exercises.id`
  - `position` integer not null
  - Prescription columns, **all nullable**: `targetSets` int, `targetReps` int, `targetWeight` real, `targetDuration` int (seconds, cardio), `targetDistance` real, `restSeconds` int, `notes` text
  - PK `(listId, exerciseId)`; unique `(listId, position)`.

API (Hono, `apps/backend`):

- `GET /api/exercise-lists` (with items, ordered), `POST /api/exercise-lists`, `PATCH /api/exercise-lists/:id`, `DELETE /api/exercise-lists/:id`
- `PUT /api/exercise-lists/:id/items` — replace-all items with positions (simplest correct reorder semantics; matches how habit reordering works).
- **Limits:** register a `max_exercise_lists` cap in `user_limits` and enforce on create; lists over the cap follow the existing frozen-resource pattern (read-only when frozen). Reuse the same error codes the tracker-freeze work established.

### Phase 2: Favorites UI

- New feature folder `apps/frontend/src/features/exercise-lists/`: list management page/panel — create, rename, delete, drag-reorder lists and their items.
- "Add to list" affordance wherever exercises are browsed (exercise picker popover rows get a small overflow/star action → submenu of the user's lists).
- Prescriptions stay hidden here: favorite-list editing shows only exercise + order. (Prescription editing arrives with routines in Phase 4 — same entity, richer editor.)
- i18n: new keys in the `tracker` namespace (or a new `lists` namespace if it outgrows ~15 keys), added symmetrically to every locale bundle per the i18n conventions doc.

### Phase 3: Picker source dropdown (the visible change)

Rework [AddExercisePicker.tsx](../../apps/frontend/src/features/activity-tracker/components/AddExercisePicker.tsx):

- Replace the static `activity_recommended` label with a **source dropdown** (small, ghost-style select above the exercise button): *All exercises*, each favorite list by name, and — once Phase 4 lands — *Today's routine*. Future source types simply append entries here.
- Drive the exercise button + popover from `useExerciseQueue(activeSource, sessionId)`:
  - The popover lists the queue in source order (search still filters; searching outside the source falls back to all exercises, clearly separated).
  - The Play button logs `entries[nextIndex]` and advances; when the source is a routine with prescriptions, `addExerciseLog` receives the prescription to pre-fill the log (sets/reps/weight targets).
- Persist last-selected source per user; default: `'all'` (or the first favorite list once one exists).
- Tooltip copy changes from "add recommended" to "add next from <source>".

### Phase 4: Programs — scheduling + prescriptions

- **`programs`** table: `id`, `userId` (owner), `authorId` (nullable, trainer), `name`, `description`, `isActive` boolean (one active program per user enforced by partial unique index), `startDate` date nullable, `createdAt`.
- **`program_entries`** table: `programId`, `listId` (the routine), and either
  - `weekday` int 0–6 (recurring weekly split), or
  - `date` date (explicit calendar assignment, for trainer-built or periodized plans);
  exactly one of the two set (check constraint). Optional `week` int for multi-week blocks.
- API: CRUD for programs/entries plus the key resolver — `GET /api/programs/active/today` → today's routine list (with prescriptions) or 404/empty. This is what the `'program'` source calls.
- Frontend: program builder page (assign existing lists to weekdays/dates), routine editor now exposes the prescription fields per item, and the picker gains the *Today's routine* source. When a program is active and has a routine today, the picker can gently suggest switching sources (non-blocking hint, not auto-switch — the user chose "dropdown with memory", not auto-pick).
- Progression rules (e.g., +2.5 kg per week) are **out of scope** for v1 of this phase; the `week` column and prescription-per-item model leave room for them.

### Phase 5: External authors & future sources

Groundwork exists (`authorId` everywhere); this phase makes it real.

- **Trainer sharing:** invitation/link between two users; trainer gets scoped write access to the trainee's lists/programs (`authorId` = trainer). Needs a permissions table + API guards; read-only view for the trainee of "who wrote this".
- **Smart source (`'smart'`):** server-computed queue from history — e.g., least-recently-trained muscle groups (the `exercise_muscle_groups` data is already in place). Pure backend endpoint returning a `ResolvedQueue`; zero picker changes.
- **AI agent source (`'agent'`):** same contract, generated by an LLM from history + goals. Requires product decisions (cost, cadence, prompt inputs) — design deliberately deferred; only the source enum slot and endpoint shape are reserved.
- Marketplace/template sharing of programs between users: future work, out of scope.

## Rollout order & dependencies

1. Phase 1 → 2 → 3 ship together as the "favorite lists" release (this alone kills the fake "Recommended" label).
2. Phase 4 is independent after Phase 1 and can ship next.
3. Phase 5 items are individually shippable; smart source is the cheapest win.

## Cross-cutting notes

- **Limits/freeze:** every new creatable resource (lists, programs) must register in `user_limits` and honor the frozen-resource enforcement from the role-limits work (2026-05).
- **i18n:** all new UI strings go through i18next with symmetric bundles across locales; system exercise names already have `nameI18n`, list/program names are user content (not translated).
- **Native app:** the Expo app (Phase 1 auth in progress) will eventually need the picker too — keeping source resolution behind API endpoints + a shared `ResolvedQueue` type in `packages/types` keeps parity cheap.
- **Existing bug to fix in passing:** the picker crashes when `exercises` is empty (`exercises[selected].name` / `.id` unguarded at lines 50 and 78) — the Phase 3 rework must handle empty queues.

## Open questions

- Should deleting an exercise that belongs to lists cascade out of the lists (current FK design: yes, via cascade on `exerciseId`) or block deletion with a warning?
- When a trainer authors a program, can the trainee edit it, or is it read-only until the trainer relationship ends?
- Does "one active program" hold, or can advanced users run overlapping programs (e.g., lifting + running)?
